## Implementation Notes

- Added the governed release naming policy pack under `config/release`:
  - `branching_policy.json`
  - `versioning_policy.json`
  - `artifact_naming_policy.json`
  - `release_channel_matrix.json`
- The branching law keeps the repo's practical two-branch posture intact while still defining the required branch families:
  - `MAINLINE` is split into `dev` as integration and `main` as admissible baseline.
  - `RELEASE_PREPARATION` uses `release/<semver>` branches for stabilization.
  - `HOTFIX` uses `hotfix/<semver>` branches with explicit baseline lineage.
  - `EXPERIMENTAL` remains preview-only and never becomes production evidence directly.
- Implemented the release derivation CLI in `scripts/release/derive_release_identity.ts`.
  - It classifies a branch against the governed branch patterns.
  - It validates branch/channel/rollout compatibility against `release_channel_matrix.json`.
  - It derives the human-facing version string, build id, rollout posture markers, and the canonical `ReleaseCandidateIdentityContract`.
  - It keeps `build_id` free of `candidate_identity_hash` so the candidate tuple can be hashed without cyclical naming.
- Implemented the artifact renderer in `scripts/release/render_artifact_names.ts`.
  - It emits deterministic names and registry coordinates for backend images, worker images, web bundles, desktop packages, SBOMs, provenance bundles, signatures, notarization companions, hardened-runtime attestations, and release-verification manifests.
  - It binds the names back to the candidate tuple through short candidate, schema-bundle, and config-bundle tokens.
  - It reuses the governed GHCR namespace families from `config/supplychain/build_target_catalog.json` instead of inventing a parallel registry layout.
- Implemented the metadata validator in `scripts/release/validate_release_metadata.ts`.
  - It rejects illegal branch/channel pairings.
  - It rejects rollout strategies whose required compatibility verdict or metadata lineage is missing.
  - It validates that release metadata remains aligned with the derived candidate identity, release-verification manifest ref, build artifact refs, and evidence naming policy.
  - It fails closed when desktop artifacts drop notarization or hardened-runtime evidence.
- Added the operator runbook `docs/release/branching_versioning_and_artifact_naming.md`.
  - It documents the branch families, version law, rollout overlays, channel admissibility matrix, artifact naming rules, and registry coordinate posture.
- Added coverage:
  - `tests/unit/release/release_identity_derivation.spec.ts`
  - `tests/integration/release/release_metadata_contract.spec.ts`
- Wired the new release paths into repo quality governance:
  - `config/tooling/code_quality_matrix.json`
  - `tests/unit/repository/code_quality_matrix.spec.ts`
  - `tsconfig.quality.json`
- Important design choices made explicit:
  - human-facing versions stay semver-based, but immutable release identity stays candidate-hash-based
  - the same commit built for two channels must diverge in both build id and human version
  - fail-forward-only posture is expressed in rollout metadata and validation, not left implicit
  - pinned-baseline and emergency promotions remain visible in naming and metadata instead of hiding in CI-only state
